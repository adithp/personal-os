# orchestrate-lanes: $ARGUMENTS

Decision 68 (replaces the loop of decision 58). Goal: a whole batch in about 1 to 1.5 hours instead of 5. Owner rules: **build everything first, test once at the end, do not fix lint as you go** (lint, typecheck, tests, build run once at the very end of the batch; memory `build-fully-then-test-once`).

## Orchestrator steps
1. **Scaffold commit** (one commit, before any lane starts): per lane, empty files and registration lines in the shared files so lanes never edit shared files. Done for habits, money, projects in commit "chore: scaffold for parallel lanes". Shared files (lanes never edit them): `packages/shared/src/index.ts`, `realtime.ts`, `packages/db/src/schema/index.ts`, `apps/server/src/actions/index.ts`, `routes/v1.ts`, `apps/desktop/src/test/fake-api.ts`, `fake-modules.ts`, `realtime/registry.ts`, `routeTree.gen.ts`, ROADMAP, DECISIONS, CONTEXT, CLAUDE.md, skills, `packages/db/drizzle/**`.
2. **Start the lane leads together** (`Agent`, `subagent_type: general-purpose`, `isolation: worktree`, `model: sonnet`, `run_in_background: true`). The lane lead is `general-purpose` because only it has the Agent tool (custom agent definitions load only after a restart). Prompt = the lane name, its scope (must / nice), and "read `.claude/skills/orchestrate-lanes/SKILL.md`, section Lane lead brief".
3. **Merge lanes one by one** (`git branch --contains <commit>` to find the branch; agent ids do not equal branch names). Docs conflicts: keep both sides. Do not commit `routeTree.gen.ts`.
4. **Migrations**: delete `packages/db/drizzle-pending/` and run one `pnpm exec drizzle-kit generate --name=<batch>` for the merged schema, then one `--custom` migration with the lanes' hand-written SQL (updated_at triggers, search triggers, Realtime publication + `GRANT SELECT` to authenticated + `REVOKE ALL` from anon). Update the migration lists in `packages/db/src/schema.test.ts`. Only the orchestrator touches `packages/db/drizzle/**`.
5. **One final check**, in parallel, all with `model: haiku`: (a) `pnpm lint` then `pnpm typecheck`; (b) packages/shared, packages/db, apps/server tests; (c) apps/desktop tests of the changed modules; (d) the rest of the desktop tests, then `pnpm build`. Failing test files are rerun alone before being called failures. Real failures and lint errors are fixed once, together (Sonnet, or me).
6. **One batch report** in `docs/reports/` (feature-report skill), DECISIONS row(s) from the lane reports, CONTEXT.md status. Nothing is ticked in ROADMAP until the owner says "next".

## Lane lead brief (read this if you are a lane lead)
You own one lane end to end inside your own git worktree. Do not push. Never read, print or edit `.env` files. Never run `pnpm db:migrate`. Local only (no Claude cloud, no claude.ai). Ask the orchestrator only if you are truly blocked or two docs contradict each other; otherwise decide yourself, write the decision down, and list it under "Decisions to confirm" in your report.

**Read first:** `CLAUDE.md` (coding principles and rules 1-10), `docs/CONTEXT.md`, `docs/LESSONS.md`, `docs/DESIGN.md`, `docs/DATABASE.md`, `docs/AI_SYSTEM.md`, your `docs/features/<module>.md`, and the `pitfalls.md` of the skills you use (new-action, api-route, db-change, data-hooks, ui-design-system, testing-patterns, time-and-money). **The Notes module is the model for every pattern** (shared schemas `packages/shared/src/notes.ts`, db `packages/db/src/schema/notes.ts`, server `actions/notes.ts` + `routes/notes.ts`, desktop `modules/notes/**`, fake API `test/fake-notes.ts`).

**Steps (code first, test once):**
1. **Research + docs (about 10-15 min):** look at 3-5 real products or references for your module (web search, Behance/Dribbble/Mobbin for the look) and write a SHORT memo (decisions only, 1-2 pages) `docs/design/research/<lane>.md`: scope (must/nice), tables, actions, screens, keyboard keys, empty/error states. Then update `docs/features/<module>.md`, DATABASE.md, API.md, AI_SYSTEM.md, DESIGN.md for the whole lane in one go (stay in your own sections; other lanes edit the same files, the orchestrator resolves conflicts).
2. **Schema once:** Drizzle schema in your own schema file(s) (`packages/db/src/schema/<lane>.ts`, already exported), RLS `ownRowsPolicy`, composite foreign keys, `user_id` on everything, money as integer paise, dates UTC. Generate the SQL with `pnpm exec drizzle-kit generate --name=<lane>` inside `packages/db`, then MOVE the new `.sql` file to `packages/db/drizzle-pending/<lane>/` (rename `0000_<lane>.sql` style, keep order prefix `01_`, `02_`) and restore `packages/db/drizzle/` (`git checkout packages/db/drizzle`, delete the new snapshot) so the journal is unchanged. Add hand-written SQL (updated_at triggers, Realtime publication + grants as in migrations 0013/0015) as further files in the same pending folder. The db test helper applies `drizzle-pending/**` after the real migrations. Put realtime table names into your `*_REALTIME_TABLES` constant in your shared file.
3. **Code first, no tests yet:** shared Zod schemas + `defineAction`s; server actions with undo (new-action skill), routes (api-route skill), registered ONLY in your scaffold files (`actions/<lane>.ts` exports your implementations array, `routes/<lane>.ts` registers your routes); desktop `modules/<module>/**` (queries, pages, components, keys, realtime-keys), your route file in `routes/_app/` (replace the placeholder), your fake `test/fake-<lane>.ts`. Start **helper agents** (Agent tool, `model: sonnet`, NO isolation so they write into your worktree, disjoint files, e.g. one for the server side and one for the UI) when the lane is big; tell them: write code and the tests they need, but do NOT run lint, typecheck or tests, do NOT commit, do NOT fix lint. You commit.
4. **One test pass (once, at the end of coding):** start 2-3 **Haiku** test agents in parallel (`model: haiku`, no edits): (a) `pnpm exec tsc --noEmit` for the packages you touched; (b) server/shared/db tests of your files (`pnpm exec vitest run <your test files>`); (c) desktop tests of your module. Fix real failures yourself; rerun flaky files alone. **Do not run or fix lint** (the orchestrator does it once at the very end).
5. **Docs sync:** every doc statement must match your code; add lessons to `docs/LESSONS.md` / pitfalls if something cost a retry.
6. **One review:** start ONE `code-reviewer`-style Sonnet agent (general-purpose, read-only instruction) that checks your diff for bugs, security (user scope on every query, RLS, destructive actions), design rules (tokens only, module color, dark/light, keyboard, empty/loading/error states) and doc drift. Apply BLOCKER and SHOULD FIX items once.
7. **Report** (final message): branch + last commit, files, migrations (the pending SQL files), what is built vs not built, "Decisions to confirm", suggested DECISIONS.md row text, lessons, manual test steps for the owner (exact steps incl. dark/light and edge cases), known issues.

**Rules:** only edit files in your lane (names containing your lane/module) plus your docs sections; never the shared files listed above; do not commit `routeTree.gen.ts` or anything under `packages/db/drizzle/`. Commit messages: Conventional Commits, end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`, add a line `[docs-ok] docs are updated in the lane docs step` (the commit hook only checks mapped docs). Money: integer paise, never floats; dates UTC stored, India days for "today" (time-and-money skill). Every data change goes through the action registry. No new libraries (Recharts, dnd-kit, TanStack, Zustand are already installed). Keep scope medium: do the **must** list well, the **nice** list only if time remains; about 60 to 75 minutes total. Mind the machine: do not start servers or Docker.
